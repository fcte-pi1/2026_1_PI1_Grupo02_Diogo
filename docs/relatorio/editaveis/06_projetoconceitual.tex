\section{Características gerais}

O projeto consiste no desenvolvimento de um micromouse, um robô autônomo que utiliza sensores e algoritmos para navegar por um labirinto e registrar os dados do percurso em tempo real. Para organizar as atividades e definir as responsabilidades da equipe, foi utilizada a Estrutura Analítica do Projeto (EAP). Essa ferramenta dividiu o trabalho de forma hierárquica em quatro áreas principais — eletrônica, software, estrutura e energia —, garantindo uma melhor gestão das tarefas e do progresso do projeto.

\subsection{Decisões de projeto}

O projeto utiliza o motor N20 (750 RPM) com roda emborrachada de encaixe direto para garantir aderência. A estrutura possui um segundo andar (fixado por espaçadores de 25 mm) para acomodar a bateria e proteger os componentes. Sem a necessidade de sensores de cor, optou-se por uma roda boba dianteira para maior mobilidade. O labirinto foi construído em MDF, garantindo leveza, resistência e facilidade de montagem.

\section{Descrição de \textit{hardware}}

O \textit{hardware} do robô MicroMouse foi projetado com o objetivo de oferecer um sistema autônomo ágil, de baixo custo e com capacidade de processamento suficiente para a execução de 
algoritmos de resolução de labirintos e controle em malha fechada. 
A arquitetura foi dividida em cinco subsistemas principais: unidade de processamento, alimentação e monitoramento,  sistema de sensoriamento, locomoção e controle, interface de depuração.

\subsection{Unidade de Processamento (Microcontrolador)}

    O núcleo do sistema é o microcontrolador ESP32. A escolha por este componente justifica-se pelo seu alto poder de processamento 
    (necessário para o cálculo de rotas e processamento de múltiplos sensores em tempo real) e pela ampla disponibilidade de pinos de Entrada e Saída de Propósito Geral 
    (GPIOs), que suportam interrupções de \textit{hardware} (essenciais para a leitura dos encoders) e modulação por largura de pulso (PWM) para o controle fino da 
    velocidade dos motores. O ESP32 opera com nível lógico de 3,3V. 

\subsection{Alimentação e Monitoramento}

    O sistema é alimentado por uma bateria de Lítio, cuja tensão nominal varia de acordo com a carga. 
    Para garantir a estabilidade do circuito, as seguintes escolhas de projeto foram feitas:
    
    \begin{itemize}
        \item Conversor Buck (LM2596-R-12): Utilizado para rebaixar e regular a tensão da bateria para 5V contínuos. 
        Esta tensão estabilizada de 5V é responsável por alimentar os sensores, a ponte H e o próprio ESP32 (através do pino VIN, que possui seu próprio regulador interno para 3,3V).
        \item Monitoramento de Energia (INA219): Para evitar a descarga profunda da bateria e monitorar o consumo instantâneo de corrente do robô, implementou-se o sensor INA219. 
        Ele se comunica com o ESP32 via protocolo I2C (pinos SDA e SCL), fornecendo dados de telemetria cruciais para a autonomia do robô.
    \end{itemize}

\subsection{Sistema de Sensoriamento}

    A percepção do labirinto é realizada por três sensores ultrassônicos HC-SR04 (posicionados, tipicamente, na frente, esquerda e direita).

    \begin{itemize}
        \item Escolha de Projeto (Divisor de Tensão): Os sensores HC-SR04 são alimentados com 5V e, consequentemente, enviam o sinal de retorno (ECHO) em 5V. 
        Como os pinos do ESP32 toleram apenas 3,3V, foi projetado um circuito divisor de tensão utilizando resistores de 1K$ \Omega $ e 2K$ \Omega $ na linha de cada pino ECHO. 
        Isso rebaixa a tensão do sinal para níveis seguros, protegendo o microcontrolador contra danos elétricos. 
        O sinal de gatilho (TRIG) é enviado diretamente pelo ESP32.
    \end{itemize}

\subsection{Locomoção e Controle}

    O deslocamento do robô é garantido por um sistema de tração diferencial composto pelos seguintes elementos:
    
    \begin{itemize}
        \item Atuadores: Motores DC N20 equipados com encoders magnéticos. 
        Os encoders fornecem o feedback de posição e velocidade (Sinais MA e MB) em malha fechada, permitindo a implementação de um controle PID para garantir que o robô 
        ande em linha reta e realize curvas precisas de 90 graus.
        \item Driver de Motor (Ponte H MX1508): O controle de sentido e velocidade (via PWM) dos motores é feito pelo CI MX1508. 
        Este componente foi selecionado por ter um formato extremamente compacto, ideal para o espaço restrito de um MicroMouse, e por suportar perfeitamente a corrente 
        demandada pelos minimotores N20.
    \end{itemize}

\subsection{Interface de Depuração}

    Para facilitar o desenvolvimento do firmware e a identificação de estados do robô durante os testes 
    (como "labirinto resolvido", "erro de leitura" ou "bateria fraca"), implementou-se um circuito de depuração com componentes de interface humana:

    \begin{itemize}
        \item Sinalização Visual e Sonora: Dois LEDs com resistores limitadores de corrente (330$ \Omega $ a 1k$ \Omega $) e um Buzzer ativo para emitir alertas.
        \item Escolha de Projeto (Acionamento do Buzzer): Como buzzers podem demandar uma corrente superior àquela que um pino GPIO do ESP32 consegue fornecer com segurança, 
        foi adicionado um transistor NPN (Q1) operando como chave. 
        O microcontrolador aciona a base do transistor (via um resistor de 1k$ \Omega $), que por sua vez permite a passagem da corrente necessária para ativar o buzzer, 
        isolando o ESP32 da carga.
    \end{itemize}

\section{Análise de consumo energético}

Abaixo, apresenta-se o detalhamento do consumo energético do sistema, considerando os componentes selecionados e o regime de operação previsto para o produto.

\begin{itemize}
    \item \textbf{Identificação dos Subsistemas Elétricos:} 
    O sistema é alimentado por uma bateria de 12V, cuja tensão é reduzida para o funcionamento dos demais componentes. O tempo estimado de operação contínua é de 7200 segundos (2 horas):
    \begin{itemize}
        \item \textbf{Microcontrolador (ESP32 DevKit):} 5V, 150mA, 7200s.
        \item \textbf{Atuadores (2x Motores N20):} 5V (via regulador), 240mA total, 7200s.
        \item \textbf{Sensores (Ultrassônicos):} 5V, 45mA, 7200s.
        \item \textbf{Indicadores (Buzzer e LEDs):} 5V, 40mA, 7200s.
        \item \textbf{Monitoramento (Sensor INA219):} 5V, 1mA, 7200s.
    \end{itemize}

    \item \textbf{Cálculo da Energia Consumida por Componente:} 
    Os cálculos foram realizados utilizando a fórmula $E = V \cdot I \cdot t$:
    \begin{itemize}
        \item $E_{ESP32} = 5V \times 0,150A \times 7200s = 5.400$ J
        \item $E_{Motores} = 5V \times 0,240A \times 7200s = 8.640$ J
        \item $E_{Sensores} = 5V \times 0,045A \times 7200s = 1.620$ J
        \item $E_{Indicadores} = 5V \times 0,040A \times 7200s = 1.440$ J
        \item $E_{INA219} = 5V \times 0,001A \times 7200s = 36$ J
    \end{itemize}

    \item \textbf{Estimativa do Consumo Total de Energia:} 
    A energia total consumida estimada para o ciclo é de \textbf{17.136 Joules}. Considerando o consumo médio de 476 mA, a demanda prevista para 2 horas de uso é de aproximadamente \textbf{952 mAh}.

    \item \textbf{Escolha da Fonte de Alimentação:} 
    O consumo total equivale a 4,76 Wh. A bateria selecionada (Li-ion 3x18650, 12V, 2000 mAh) fornece 24 Wh, garantindo uma margem de segurança superior a 50\%, o que é ideal para compensar perdas térmicas e picos de corrente.

    \item \textbf{Planejamento do Circuito de Alimentação:} 
    Utiliza-se o regulador de tensão \textbf{LM2596 (Step-Down)} para converter os 12V da bateria em 5V estáveis. O circuito conta com o sensor \textbf{INA219} para monitoramento de corrente e tensão, servindo como proteção contra sobrecargas.

    \item \textbf{Monitoramento via \textit{software}:} 
    O ESP32 realiza a leitura do sensor INA219 via código, permitindo acompanhar o consumo em tempo real e registrar o tempo de operação para evitar a descarga profunda da bateria.

    \item \textbf{Validação com Testes Reais:} 
    A validação compara a autonomia teórica com a real. Diferenças encontradas são atribuídas à eficiência do LM2596 (80-90\%) e dissipação por Efeito Joule nos condutores.
\end{itemize}

            \item \textbf{Descrição das Funcionalidades:} 
            A interface foi projetada seguindo a estética \textit{Mission Control}, priorizando a visualização de dados críticos em tempo real. O dashboard é composto por:
            \begin{itemize}
                \item \textbf{Grid Dinâmico (16x16):} Renderização central do labirinto com atualização de trajeto conforme o mapeamento do robô.
                \item \textbf{Fluxo de Eventos (Logs):} Painel lateral dedicado ao rastreio de decisões do algoritmo e status de conexão.
                \item \textbf{Widgets de Telemetria:} Monitoramento de consumo de bateria (tensão/corrente), velocidade média e sensores de distância (ToF).
                \item \textbf{Status da Missão:} Indicadores de tempo de conclusão e validação do desafio cumprido.
            \end{itemize}
        \end{itemize}

    \item \textbf{Arquitetura do software:}
    \begin{itemize}
        \item \textbf{Propósito:}
        O \textit{software} atua como o núcleo de inteligência e monitoramento do sistema (Mission Control). Sua função é processar a telemetria enviada pelo robô em tempo real, gerenciar a construção dinâmica do mapa do labirinto, executar algoritmos de \textit{pathfinding} para determinar a rota otimizada e fornecer uma interface gráfica para visualização de métricas de energia e desempenho.
    
        \item \textbf{Arquitetura:}
        Arquitetura Orientada a Eventos (\textit{Event-Driven Architecture}) com Monólito Modular no \textit{backend}. Este padrão permite lidar com a natureza assíncrona dos dados de sensores, garantindo que o sistema reaja a eventos instantâneos sem latência perceptível. Como stack principal tem-se como:
        \item \textbf{Diagrama de alto nível:} 
        A arquitetura segue um fluxo de dados linear e reativo, conforme descrito abaixo:
        
        \begin{figure}[H]
            \centering
            \includegraphics[width=0.9\textwidth]{figuras/diagrama_arquitetura.png}
            \caption{Fluxo de dados e arquitetura da solução.}
            \label{fig:arquitetura}
        \end{figure}
    
    \begin{enumerate}
        \item \textbf{ESP32:} Coleta dados de sensores e publica pacotes JSON via \textbf{MQTT} no tópico \texttt{rato/telemetria}.
        \item \textbf{Broker Mosquitto:} Recebe as mensagens e as encaminha para os assinantes ativos.
        \item \textbf{Node.js (\textit{Back-end}):} Atua como assinante (\textit{subscriber}) do broker, processa os dados recebidos, realiza a persistência no \textbf{PostgreSQL} e emite eventos via \textbf{WebSockets}.
        \item \textbf{React (\textit{Front-end}):} Escuta os eventos emitidos pelo servidor e renderiza instantaneamente o labirinto e os gráficos de consumo energético.
    \end{enumerate}

        \item \textbf{Tecnologias:}
            \begin{itemize}
            \item \textbf{Linguagens de programação:} JavaScript (ES6+) e C++.
            \item \textbf{\textit{Frameworks}, bibliotecas e protocolos:} No \textit{front-end}, utiliza-se \textbf{React (Vite)} com \textbf{Tailwind CSS}. No \textit{back-end}, \textbf{Node.js}, \textbf{Express} e \textbf{Socket.io}. Para o \textit{firmware}, o \textit{framework} \textbf{Arduino} via \textbf{PlatformIO}. A comunicação é regida pelos protocolos \textbf{MQTT} (entre ESP32 e Broker) para telemetria leve e \textbf{WebSockets} (entre Backend e Frontend) para atualização em tempo real.
            \item \textbf{Banco de dados:} Relacional \textbf{Prisma ORM} e \textbf{PostgreSQL} via Docker.
            \end{itemize}

    \item \textbf{Persistência de dados:}

\section{Persistência de Dados}

O sistema utiliza PostgreSQL e Prisma ORM para persistência de dados, modelando a estrutura física dos labirintos e o histórico de execuções do \textit{micromouse}. O Modelo Entidade-Relacionamento (MER) foi projetado para assegurar a rastreabilidade da telemetria e a integridade da auditoria de sistema.

\subsubsection*{Entidade Maze}
Elemento central da modelagem do ambiente, representa um labirinto cadastrado e suas dimensões físicas padrão.
\begin{multicols}{2}
\begin{itemize}
    \item id; \item name; \item width; \item height; \item createdAt.
\end{itemize}
\end{multicols}

\subsubsection*{Entidade Cell}
Mapeia uma célula individual, sua posição $(x,y)$ na matriz e a existência de paredes nas direções cardeais. Possui restrição de unicidade composta (\textit{mazeId}, \textit{posX}, \textit{posY}).
\begin{multicols}{2}
\begin{itemize}
    \item id; \item mazeId; \item posX; \item posY; \item wallNorth; \item wallSouth; \item wallEast; \item wallWest.
\end{itemize}
\end{multicols}

\subsubsection*{Entidade Session}
Registra uma execução completa do robô, armazenando o algoritmo, modo de operação, métricas de desempenho e dados energéticos coletados durante a corrida.
\begin{multicols}{2}
\begin{itemize}
    \item id; \item sessionName; \item algorithm; \item mode; \item createdAt; \item durationMs; \item avgSpeed; \item isCompleted; \item startPosX; \item startPosY; \item initialVoltage; \item finalVoltage; \item totalDrainMah; \item fastestPath; \item mazeId.
\end{itemize}
\end{multicols}

\subsubsection*{Entidade SessionStep}
Registra a evolução temporal da telemetria, permitindo a reconstrução exata do percurso e do consumo a cada instante da execução.
\begin{multicols}{2}
\begin{itemize}
    \item id; \item sessionId; \item timestamp; \item stepOrder; \item posX; \item posY; \item voltage; \item current; \item consumption.
\end{itemize}
\end{multicols}

\subsubsection*{Entidades de Telemetria (Log e Raw)}
A entidade \textbf{\textit{TelemetryLog}} armazena eventos do sistema para diagnóstico. A \textbf{\textit{TelemetryRaw}} guarda mensagens MQTT em formato bruto (\textit{payload} JSON) para auditoria completa.

\begin{multicols}{2}
\textbf{Atributos (TelemetryLog):}
\begin{itemize}
    \item id; \item sessionId; \item timestamp; \item logType; \item message.
\end{itemize}
\columnbreak
\textbf{Atributos (TelemetryRaw):}
\begin{itemize}
    \item id; \item createdAt; \item topic; \item robotId; \item payload.
\end{itemize}
\end{multicols}

\subsubsection*{Relacionamentos e Cardinalidades}
Os relacionamentos definidos no esquema do Prisma garantem a integridade referencial do sistema:
\begin{multicols}{2}
\begin{itemize}
    \item \textbf{Maze -- Cell (1:N):} Labirinto possui várias células.
    \item \textbf{Maze -- Session (1:N):} Labirinto utilizado em múltiplas sessões.
    \item \textbf{Session -- SessionStep (1:N):} Sessão composta por múltiplos passos.
    \item \textbf{Session -- TelemetryLog (1:N):} Sessão gera múltiplos logs de auditoria.
\end{itemize}
\end{multicols}
